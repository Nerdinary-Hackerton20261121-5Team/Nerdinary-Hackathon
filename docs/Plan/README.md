# Plan — 원본 조회와 백업

Notion 공통 시작 문서와 집중 세션 [기획서 v0.13](PROJECT.md)와 [기능명세](FEATURES.md)·[정책서](POLICIES.md) v0.12 초안을 등록하고 조회 사본을 확보했다.
시작 전 4명은 12조각, 5명은 10조각, 6명은 12조각으로 미리 나눠 한 사람당 2~3개씩 배정한다. 집중 중 타인의 조각은 최대 블러로 보인다. 공동 조립을 시작하면 각 조각은 소유자가 집중 시간에 복원한 모습 그대로 모든 참가자에게 보인다. 집중 화면 좌상단에는 본인 카메라, 나머지 공간에는 타인 조각을 무작위로 배치한다. 조립 때는 중앙에 판, 좌우에 무작위로 섞인 조각을 표시한다. 완성 블록을 누르면 소유자와 최종 복원도를 볼 수 있다. 공동판에서는 각자 자기 조각만 옮길 수 있고, 모든 조각이 제자리에 놓이면 팀이 통과한다. 잘못 놓으면 해당 조각만 드래그 직전 위치로 돌아가고 소유자는 바로 다시 놓을 수 있다. 세션 이미지 필터는 검토 중이다.
비회원 코드 입장과 랜덤 매칭을 먼저 진행한다. 랜덤 매칭 대상은 개설자가 랜덤 참가를 허용한 대기방의 빈자리다. 로그인과 마지막 세션으로의 계정 자동 복귀는 후순위다. 집중 종료 시 부재한 참가자 몫의 조각은 마지막 복원 모습으로 정답 칸에 자동 배치한다.
Design은 GitHub를 사용할 수 없으므로 Notion 원본에서 문서·검토, Figma에서 디자인을 확인한다.
workspace.notion과 plan.project·plan.features·plan.policies에 원본이 등록되어 있다. 기능별 필요한 범위는 [발췌 사본](features/README.md)에서 찾는다.
[화면 정보구조](IA.md)와 [사용자 흐름도](diagrams/INDEX.md)는 MVP에 업로드한 기획 시안이다. 나머지 미등록 자료는 빈 양식이다. 초안의 조회 사본을 개발 전달 완료본으로 취급하지 않는다.
[원본 목록](../start/SOURCES.yaml)과 [백업 기록](BACKUP_MANIFEST.yaml)을 함께 사용한다.

## 자료별 기준

| 자료 | 원본 | 사본 또는 연결 |
|---|---|---|
| 기획·정책·담당표·결정·IA·QA·발표 | 등록된 Notion | Plan의 해당 Markdown |
| 화면·다이어그램 | 등록된 Figma·FigJam 등 | 디자인·다이어그램 인덱스, SVG·PDF |
| 화면 동작 설명 | 등록된 Notion 또는 Figma 설명 | 화면 ID에 연결된 화면설계 |
| 코드·API·데이터 계약·통합·개발 인계 | 저장소 | Coding 문서가 정의 위치를 연결 |

원본의 최신 편집본과 개발에 적용할 전달 완료본을 구분한다.
정책 원본과 디자인 원본처럼 종류가 다른 자료를 수정 시각만으로 서로 대체하지 않는다.

## 읽기 순서

1. SOURCES.yaml에서 담당 기능·화면·정책의 원본 링크와 fallback_path를 찾는다.
2. 연결 도구로 원본의 현재 적용 개정본과 필요한 범위를 읽는다.
3. 지원되지 않거나 접근할 수 없으면 허용된 공유 링크·브라우저 방법을 확인한다.
4. 이미 확보한 동일 버전·범위는 재사용한다. 내용이 없으면 캐시 또는 원문을 읽는다.
5. 온라인 자료를 읽을 수 없으면 최신 원격 main의 사본과 BACKUP_MANIFEST를 함께 확인한다.
6. 변경·누락·적용 개정의 차이를 확인하고 현재 작업에 사용할 기준을 명시한다.

문서 제목·로그인 화면·썸네일만 읽힌 것은 본문 확인이 아니다.
하위 페이지·표·이미지·프레임 상태가 일부 누락됐으면 읽힌 범위와 빠진 항목을 기록한다.
역할별로 필요한 범위를 충분히 읽었는지가 기준이며 전체 파일 조회가 항상 필요한 것은 아니다.
권한·플랜 한도·지원 불가에서는 같은 호출을 반복하거나 제한 우회를 시도하지 않는다.

## 백업 최신성

가까운 커밋 시각만으로 최신이라고 판단하지 않는다.
원본 URL·자료 ID·개정·확인 가능한 수정 시각·조회 시각·내보낸 시각·포함 범위를 비교한다.
상위 페이지의 수정 시각만으로 연결된 하위 자료 전체가 같다고 보증하지 않는다.
개정 정보를 얻지 못하면 담당자가 지정한 전달 버전과 확인된 범위를 기록하고 한계를 표시한다.

- 원본과 일치한 사본: 해당 범위에 사용.
- 원본 접근 불가, 마지막 확인 개정만 알려짐: 마지막 확인본으로 표시.
- 백업 이후 변경이 알려졌으나 반영 여부 미확인: 영향받는 작업만 확인 대기.
- 원본·백업 충돌: 차이를 보고하고 임의 결합하지 않음.
- 원본 미등록: 빈 양식을 실제 요구사항으로 적용하지 않음.
- 원격 미생성·오프라인: 최신 원격 main을 확인했다고 하지 않음.

예를 들어 수정 전달 시각보다 이전 원본의 사본은 나중에 커밋했더라도 새 수정의 근거가 아니다.
특정 과거 시점의 자료를 요청받았으면 그 시점·개정을 지정해 조회하고 현재본과 구분한다.

## main 문서 확인

원격이 구성된 후 실제 원격 main의 커밋과 조회 시각을 확인한다.
작업 브랜치를 강제로 바꾸거나 pull·reset으로 진행 중인 변경을 덮어쓰지 않는다.
필요한 원격 참조의 파일을 별도로 읽고 적용한 커밋을 개인 조회·인계 기록에 남긴다.
main 반영 전 로컬 사본은 '로컬 준비본'으로 표시한다.
현재 비공개 GitHub 원격과 main 브랜치가 있다. [초기 설정 기록](../start/REPOSITORY_SETUP.md)은 첫 업로드 확인 근거다.
main의 Plan 문서는 여전히 원본 미등록 빈 양식이다. 최신 원격 상태는 필요한 시점에 다시 조회한다.

## 사본 갱신

원본 담당이 개발 전달, 주요 정책 변경, 디자인 인계, 통합 직전에 필요한 자료를 갱신한다.
1. 적용할 원본 개정과 포함 범위·담당을 확인한다.
2. 필요한 본문·표·자산을 확보하고 서로 연결된 자료의 기준이 맞는지 확인한다.
3. 정상 확보한 자료로 해당 사본을 갱신하고 누락·내보낸 결과를 기록한다.
4. 사본 헤더의 source_revision·captured_at·status와 BACKUP_MANIFEST를 함께 갱신한다.
5. SVG·PDF는 실제 열어 잘림·글자·누락을 확인한 범위만 검증했다고 기록한다.
6. 승인된 저장소 운영 절차로 반영하고, main에 포함된 뒤에만 main 사본으로 표시한다.
실패·빈 응답으로 기존 유효한 사본을 덮어쓰지 않는다.
부분 사본이 필요한 경우 남은 범위를 명시하고 완전한 전달본처럼 표시하지 않는다.

Markdown 사본의 status는 unregistered_blank / snapshot / partial 중 실제 상태를 기록한다.
manifest의 state는 unregistered_blank / snapshot / partial / stale_known으로 구분한다.
backup_files에는 실제 확보한 파일만 넣고 빈 예약 경로는 reserved_path로 구분한다.
전달 묶음에 연결된 자료가 다른 기준이면 차이를 먼저 확인한다.
원본과 사본을 별도로 독립 편집하지 않는다. 수정 제안은 원본 담당에게 전달한다.
과거 사본은 Git 이력으로 보존하고 기본 경로는 최신 사본을 유지한다.

## 비용과 확인 시점

기능별 작은 Notion 페이지·특정 Figma 프레임·짧은 변경 목록을 사용한다.
도구가 지원할 때만 변경 정보 위주로 조회하며 그런 기능이 있다고 가정하지 않는다.
전체를 받은 뒤 요약하는 것만으로 최초 조회 비용이 줄어들지는 않는다.
같은 버전·범위의 자료를 테스트마다 다시 읽지 않는다.
작업 시작·관련 변경 전달·통합·인계 때 재확인한다. 자동 감시는 현재 구성되어 있지 않다.
