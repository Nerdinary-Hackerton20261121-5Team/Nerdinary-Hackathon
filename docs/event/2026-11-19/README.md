## PM과 구현 계획에 직접 영향을 주는 내용

아래는 공식 안내의 요약이며 팀의 제품 결정이나 작업 배정이 아니다.

1. **근거 있는 문제 정의와 작은 MVP.** PM은 데이터·인터뷰·설문·실제 사례의 출처와 조사 시점을 제시해야 한다. 사실과 가설을 구분하고 문제 → 원인 → 해결 방향 → 기대 효과를 연결한다. 핵심 기능만으로 주요 사용자 과업을 끝까지 완료하는지가 기능 최적화의 핵심이다.
2. **핵심 사용자 흐름을 보여 주는 화면.** 정보구조도 또는 사용자 플로우 차트와 주요 화면을 제시한다. 목적 달성 흐름, 정보·버튼·결과 안내를 설명한다. 기획·발표·시연의 일관성, 역할 분담과 의견 조율·피드백 반영도 평가한다.
3. **불필요한 로그인과 기능 확대를 줄이는 가이드.** PM·Web은 로그인·회원가입의 필요성을 점검하고, Server 가이드는 로그인 제외를 권고한다. 이를 로그인 금지 규칙으로 해석하지 않는다.
4. **Web도 앱 결과물이 평가 대상.** 모바일 뷰를 기본으로 설계하고 앱 변환 시간을 확보하도록 안내한다. 앱 실행은 Android/iOS 각각 5점, 네이티브와 웹의 연결은 10점이다. 웹에서만 동작하고 앱에서 안내 없이 실패하면 연결 점수에서 건당 2점 감점이다.
5. **Server의 별도 새벽 4시 마감.** 인프라 구성도와 ERD를 제출하고 API 연동 가능한 인프라를 완료해야 한다. 폼 제출이 04:00 이후이거나 구성도·ERD 미제출이면 인프라·DB 항목은 0점이다. 행사 흐름상 11/22 새벽으로 해석하되 원문의 표기는 ‘새벽 4시’다.
6. **실제 서버 연결과 접근 가능한 증빙.** Server는 클라우드 배포, 접근 가능한 URL, API 명세, 코드 저장소 URL이 요구된다. 인프라 항목은 localhost이면 0점이다. Web의 API 항목에서는 localhost 통신도 인정한다고 별도로 안내하므로 역할별 기준을 혼동하지 않는다.
7. **릴리즈 상태와 오류 대응.** Android·iOS는 Release 빌드와 기능명세서 기준으로 평가한다. 크래시(및 Android ANR)가 발생하면 안정성 항목은 0점이다. Server는 전역 예외처리와 기본 응답·오류 코드를 구분해야 한다.
8. **AI 활용 안내는 확인됨.** Web 유의사항은 마크업의 AI 활용과 Figma MCP 등을 권장한다. 사전 제작물·기존 코드 재사용·AI 사용 전체 범위의 별도 허용 규정은 찾지 못했다.

## 설명 차이와 아직 확인할 정보

- **와이어프레임:** PM 유의사항은 생략 후 바로 디자인을 권하며 Design 유의사항·가이드는 빠른 와이어프레임 정리를 안내한다. 별도의 긴 단계를 줄이라는 방향으로 해석할 수 있으나, 단일 강제 규칙으로 바꾸지 않는다.
- **시간 구간:** 역할별 ‘최종 점검·발표 준비’는 05:00~07:40이지만 제출 마감은 명시적으로 07:30이다. 발표 준비 구간의 끝을 제출 연장으로 해석하지 않는다.
- **Web API 배점:** ‘전체 API 연동 20점’과 ‘2개 이하 연동 5점’이 함께 있어 전체 API 자체가 2개 이하인 경우의 우선 기준은 미기재다. 점수를 위해 불필요한 API를 추가하는 결정은 하지 않았다.
- **가산점:** Web은 최대 10점 중 설명된 5점 외 항목이 불명확하고, iOS는 세부 가산점 항목이 없다.
- **앱 제출 형태:** Web의 APK 관련 설명과 Android/iOS 각 실행 점수는 확인했지만 iOS 제출·설치 방식, 허용 앱 변환 방식, 전체 최종 제출 패키지·제출 경로는 미기재다.
- **행사 주제·팀 구성·발표:** 실제 주제, 팀별 인원과 배정 방식, 발표·QnA 시간 배분, 전체 합산·동점 처리, 수상 내역은 미기재다.
- **사전 작업·도구:** 사전 개발과 기존 코드·템플릿 재사용 범위, 유료 외부 서비스·AI 사용의 전체 규정은 미기재다.
- **제출 폼:** Google 로그인 화면까지만 확인했다. 내부 질문, 제출 파일 형식·개수·용량 제한은 미확인이다.

## 이후 아이디어 논의에 적용할 제안

공식 주제는 당일 발표 일정이므로 지금은 사용자 문제 후보와 근거를 준비하고, 주제 발표 후 연결 가능한 아이디어를 고르는 방식이 적절하다. 후보를 비교할 때는 문제의 근거, 작은 핵심 흐름의 완결성, 실제 API 연결, 앱 결과물 및 시간 내 제출 가능성을 함께 확인한다. 이는 수집 내용을 바탕으로 한 제안이며 확정된 팀 기획은 아니다.
